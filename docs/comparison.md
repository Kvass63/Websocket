# Сравнение WebSocket и SSE

Таблица заполняется на шаге 5. Цифры берутся только из реальных запусков
бенчмарка (файлы в `bench/results/`). Пустая ячейка значит «ещё не измерено».

## Условия измерений

- Машина: настольный ПК, Intel Core i5-14600KF (14 ядер, 20 потоков),
  31,8 ГБ памяти, Windows 10 Pro. Все замеры в таблице сделаны на ней
  23.10.2026, сервер и клиенты бенчмарка на одной машине
- Версия Python: 3.14; библиотеки по `requirements.txt`: fastapi 0.143.0,
  uvicorn 0.54.0, websockets 17.2, httpx 0.28.1, psutil 7.2.2
- Команда запуска сервера: `uvicorn app.main:app --no-access-log`, один
  процесс, без `--reload`
- Порядок: для каждого N — перезапуск сервера, затем подряд WS, WS без
  сжатия, SSE, у каждого 3 прогона. Память измерена отдельно (см. ниже)
- Параметры бенчмарка: M = 200 сообщений, интервал 20 мс, тайм-аут
  ожидания 30 с, текст 100 символов; 3 прогона на каждое N, в таблице
  медиана по каждому показателю отдельно
- Исходные данные: `bench/results/<транспорт>_n<N>_run<K>.csv`
- Клиенты: отправитель `u0` в главном процессе, остальные N − 1 клиентов
  поровну в 4 дочерних процессах
- WebSocket — со сжатием кадров (permessage-deflate), как в браузере;
  столбец «WS без сжатия» — тот же тест с `--no-deflate`
- CPU — в процентах от одного ядра (так считает `psutil`): 100 % значит,
  что процесс полностью занял одно ядро. Сервер работает в одном потоке,
  поэтому его предел — около 100 %
- CPU при N = 10 малоинформативен: Windows учитывает время процессора
  шагами около 15,6 мс, и при малой нагрузке замеры по 0,5 с часто
  получаются 0.0

«Доставок в секунду» — сколько сообщений сервер реально доставил за
секунду окна замера (от первой отправки до последней доставки). Заданный
темп — N получателей × 50 сообщений в секунду. Пока сервер успевает,
число равно заданному темпу и ничего не говорит о сервере; если оно
меньше, сервер упёрся в предел, очередь растёт, и задержка в этой строке
таблицы показывает в основном рост очереди за 4 секунды отправки. На
машине замеров сервер успевал при всех N у всех трёх транспортов, так что
задержка в таблице — это сама доставка, а не рост очереди.

«Память сервера, свежий сервер» — `rss_max_mb` первого прогона сразу
после запуска сервера, отдельно для каждого транспорта и N. Медиану трёх
прогонов из CSV для памяти брать нельзя: Python не возвращает системе
освободившуюся память, и на одном сервере она растёт от прогона к
прогону (у WS при N = 500: 187 → 313 → 398 МБ), то есть зависит от того,
что запускали до этого. Столбец WebSocket — это `ws_n<N>_run1.csv` (WS
шёл первым после перезапуска). Столбцы «WS без сжатия» и SSE — отдельные
запуски `--runs 1`, каждый на только что запущенном сервере; их CSV не
сохранены (они перезаписали бы финальные `run1`), значения переписаны из
вывода бенчмарка. Почти во всех запусках `rss_max_mb` равен `rss_start_mb`
(памяти перед окном замера): память занимают соединения, а за время
отправки сообщений она не растёт.

Память на одно соединение (расчёт: из памяти при N = 500 вычесть ~50 МБ
пустого сервера и поделить на 500; при N = 100 получается так же): WS со
сжатием ~0,27 МБ, WS без сжатия ~0,10 МБ, SSE ~0,11 МБ.

«CPU клиентов» — загрузка самого занятого из процессов бенчмарка
(`client_cpu_max`). Если она близка к 100 %, тестовый скрипт сам не
успевает разбирать сообщения, и задержка завышена из-за него, а не из-за
сервера.

Ограничение метода: клиенты бенчмарка работают на той же машине, что и
сервер, и делят с ним процессор. Разнесение клиентов по нескольким
процессам снимает упор в одно ядро у самого скрипта, но не конкуренцию
за процессор с сервером.

### Как проверяли, что задержку можно считать в разных процессах

`cts` ставит главный процесс, а время получения — дочерние, поэтому
значения `time.perf_counter()` из разных процессов вычитаются друг из
друга. Документация Python этого не гарантирует, поэтому проверили:
главный процесс запоминает `t1`, просит дочерний прислать свой
`perf_counter` (`t2`) и запоминает `t3`, когда получил ответ. Если
счётчик общий для системы, всегда `t1 ≤ t2 ≤ t3`.

Результат (Python 3.14.3, Windows 11): 200 обменов, нарушений 0. Самый
быстрый обмен занял 0,032 мс, значит, расхождение счётчиков, если оно
есть, меньше 0,032 мс — на порядки меньше измеряемых задержек. Проверка
делалась на ноутбуке, а не на машине замеров (там Windows 10).

### Наблюдения по результатам

- Сжатие у WebSocket (permessage-deflate) на коротких сообщениях не
  окупается. При N = 500 WS со сжатием по сравнению с WS без сжатия:
  задержка 6,61 против 4,41 мс, CPU сервера 62,8 против 39,5 %, память
  186,9 против 102,2 МБ. Сообщение — 100 символов, сжимать почти нечего,
  а работа на каждый кадр и состояние сжатия на каждое соединение
  остаются. Объяснение памяти не измерено: так ведёт себя zlib, который
  для каждого соединения держит своё окно и таблицы сжатия.
- SSE медленнее WS без сжатия при всех N, но разрыв сокращается с ростом
  N: при N = 10 среднее 1,70 против 0,49 мс (в 3,5 раза), при
  N = 500 — 7,78 против 4,41 мс (в 1,8 раза). Причину бенчмарк не
  показывает. Предположение (не проверено): у SSE каждое сообщение
  начинается с отдельного HTTP-запроса POST, это постоянная добавка,
  заметная, пока остальная задержка мала.
- SSE без сжатия и WS без сжатия занимают почти одинаково памяти
  (~0,1 МБ на соединение).
- Массовый уход клиентов порождает лавину событий `leave`: каждый ушедший
  клиент — одно сообщение каждому оставшемуся, при 500 клиентах до
  ~125 000 сообщений за доли секунды. В конце одного из прогонов SSE
  N = 500, когда бенчмарк закрывал клиентов, сервер выкинул как медленных
  375 клиентов (очередь 100 сообщений переполнилась). В замер это не
  попало: `kicked` считается до закрытия клиентов и во всех прогонах
  равен 0. Выкинуты были блоки ников, совпадающие с тем, как клиенты
  разложены по процессам: процесс, занятый закрытием своих соединений, не
  успевал читать остальные.
- Остановка сервера после замеров зависала: после `Shutting down` uvicorn
  не завершался. В логе перед этим были ошибки
  `ConnectionResetError [WinError 10054]`: клиент оборвал соединение
  сбросом (RST), и при закрытии сокета на сервере `socket.shutdown()`
  выбросил исключение. По исходникам asyncio
  (`proactor_events.py`, `_call_connection_lost`) после этого исключения
  не выполняется `server._detach()`, сервер asyncio считает соединение
  живым, и uvicorn при остановке вечно ждёт `server.wait_closed()`.
  Помогает флаг `--timeout-graceful-shutdown 1`: по исходникам uvicorn это
  ожидание входит в ограниченное по времени ожидание. На замеры не
  влияет: всё происходит уже после окна замера.
